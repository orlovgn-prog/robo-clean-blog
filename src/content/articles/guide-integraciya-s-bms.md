Робот-уборщик, работающий изолированно, — уже полезен. Но когда он интегрирован с системой управления зданием (Building Management System, BMS), возможности выходят на новый уровень: автоматический вызов лифта, уборка по датчику заполненности, синхронизация с HVAC. Разбираемся, как это устроено.

## Зачем нужна интеграция

Типичные сценарии, которые возможны только при связке робота и BMS:

**Вызов лифта.** Робот отправляет команду через BMS, лифт приезжает на нужный этаж, двери открываются, робот заезжает. После уборки этажа — возвращается тем же путём. Без интеграции робот работает только в пределах одного этажа.

**Уборка по событию.** Датчик проходимости в BMS фиксирует, что через холл прошло более 500 человек — автоматически запускается внеплановая уборка. Или после корпоративного мероприятия система запускает робота в конференц-зону.

**Синхронизация с освещением.** BMS включает свет в зоне, где работает робот, и выключает после его прохода — экономия энергии при ночной уборке.

**Климат-контроль.** Робот подаёт сигнал о начале влажной уборки, BMS увеличивает вентиляцию для быстрого высыхания пола.

**Контроль доступа.** Робот получает временный доступ в закрытые зоны (серверные, переговорные) через интеграцию с СКУД.

## Протоколы и интерфейсы

Интеграция робота с BMS может быть реализована на нескольких уровнях:

**REST API.** Большинство современных роботов (Avidbots, Gausium, Brain Corp) имеют открытый API для управления и получения статуса. BMS-платформа отправляет HTTP-запросы для запуска миссий, получения местоположения, чтения отчётов.

**MQTT.** Лёгкий протокол для IoT-устройств. Робот публикует свой статус (местоположение, состояние батареи, текущая миссия) в MQTT-топик, а BMS подписывается на него. Используется в Gausium Cloud.

**BACnet / Modbus.** Классические протоколы BMS. Робот обычно не говорит на них напрямую, но через middleware-шлюз (например, на базе Node-RED или специализированного контроллера) можно транслировать API-вызовы в BACnet-объекты.

**ROS 2 (Robot Operating System).** Низкоуровневый протокол для робототехники. Используется для глубокой интеграции с навигационными системами здания, умными дверями, лифтами. Требует инженерной экспертизы.

## Архитектура интеграции

Рекомендуемая архитектура для бизнес-центров:

1. **Облачная платформа робота** (Avidbots Command Center, Gausium Cloud) — управление миссиями, расписание, отчёты
2. **Middleware-слой** (Node-RED, Home Assistant, специализированный шлюз) — трансляция протоколов, бизнес-логика, триггеры событий
3. **BMS-платформа** (Honeywell, Siemens Desigo, Johnson Controls Metasys) — управление инженерными системами здания
4. **Локальная сеть** — отдельный VLAN для IoT-устройств с контролем доступа

Middleware-слой — ключевой элемент. Именно он связывает разные протоколы и реализует бизнес-логику: «если датчик проходимости показал N человек за час, запустить миссию X».

## Интеграция с лифтами

Самый востребованный и сложный сценарий. Два основных подхода:

**Через API лифтовой системы.** Производители вроде KONE, Otis, Schindler предлагают облачные API (KONE API, Otis ONE) для вызова лифта третьими системами. Робот через middleware вызывает лифт, получает уведомление о прибытии, заезжает.

**Через аппаратный контроллер.** Для старых лифтов без API используется контроллер, физически подключённый к лифтовой панели. Эмулирует нажатие кнопки вызова. Менее элегантно, но работает.

## Подводные камни

- **Разные часовые пояса и форматы времени** в системах робота и BMS — частая причина рассинхронизации расписаний
- **Сетевая безопасность** — робот не должен иметь доступ к критическим системам здания (пожарная сигнализация, СКУД). Используйте сегментацию сети
- **Задержки сети** — при вызове лифта задержка более 3–5 секунд может привести к тому, что робот «потеряет» лифт
- **Отсутствие стандартов** — каждый производитель роботов и BMS использует свои API, универсального стандарта пока нет
